# 迁移

适用于数据结构/数据本身、公共接口或协议、语言运行时、框架、依赖体系、存储或基础设施从旧状态转换到新状态。迁移的核心是管理转换期间的兼容性、数据正确性和失败恢复。

## 1. 描述源状态与目标状态

确认当前版本/结构、目标版本/结构、受影响组件和调用方、迁移规模、运行窗口、所有权与环境。目标不清楚或缺少关键约束时按 [clarification.md](clarification.md) 处理。涉及实际数据、生产系统或外部状态时，明确批准边界和执行条件；不要从“开发迁移方案”推断为“已授权上线或修改真实数据”。

## 2. 分析转换性质

根据任务检查：

- 旧新版本能否共存，是否需要向后/向前兼容；
- 转换是否幂等、可重复、可分批或可暂停；
- 数据完整性、映射、默认值、丢失和重复风险；
- 双写/回填/切换/清理阶段及各阶段的完成证据；
- 失败后的回滚、前滚或恢复办法；
- 部署顺序、观察指标、切换条件和停止条件。

不相关的检查项可以省略，但必须说明会影响本迁移安全性的因素。

## 3. 设计和计划

有重要技术取舍时写 Design；跨组件或多阶段转换时写 Plan；行为/数据规则复杂时写 Spec；长期有效的兼容或平台约束同步到项目文档，只有其选择原因未来仍需解释时才写 ADR。模板按需使用 `../assets/` 中相应文件。复杂或有数据风险的迁移，在执行前明确可验证的预演或核对方式。

常用阶段形状为：兼容准备 → 转换/回填 → 校验 → 切换 → 观察 → 移除旧路径。并非每项迁移都需要全部阶段；依据真实系统约束选择。

## 4. 执行和验证

按计划逐阶段核验状态、数量/校验和/语义约束、接口兼容和运行健康。每个阶段定义继续、停止、恢复的条件。失败时先确认当前真实状态再恢复，不假定回滚必然安全。没有实际运行迁移时，只能报告方案或离线验证结果，不能称生产迁移完成。
