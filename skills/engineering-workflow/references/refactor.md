# 重构

适用于改善内部结构、可维护性或可演进性，并以保持对外可观察行为不变为目标。若本次同时要求改变产品行为，应把行为变化明确拆出并按 [feature.md](feature.md) 路由。

## 1. 界定行为边界

说明重构目的、涉及范围、必须保留的接口/格式/副作用及已知调用方。检查当前实现、用法、配置和可用验证证据。不能仅因代码看起来不理想就假定可以改变其行为。

## 2. 准备行为保护

识别最重要的调用路径、输入输出、错误行为、持久化格式和兼容条件。优先使用项目现有检查；缺少保护时根据风险选择必要的验证补充。高风险或范围较大的重构，可先写短 Plan；若方案本身有重要边界决策，再补 Design。

## 3. 小步实施

每一步保持系统可理解并尽早核验行为。优先分离结构整理与产品行为变化，避免无关格式化、依赖升级或架构重写混入。若必须改变行为，暂停原定“纯重构”假设并重新确认范围。

## 4. 完成判定

检查对外契约、关键路径和项目要求的验证。总结结构上的改变，并报告实际验证结果及无法覆盖的风险。若重构揭示了独立设计问题，可记录为后续任务，不默认扩大当前范围。
