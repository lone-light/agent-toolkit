# Bug 修复

适用于系统实际行为与已确定的预期行为不一致。若预期尚不清楚，先按 [clarification.md](clarification.md) 澄清；若所谓 Bug 实际是新增需求，则转入 [feature.md](feature.md)。

## 1. 确认问题

收集最小而充分的问题描述：触发条件、输入或环境、实际结果、预期结果、影响范围和可用证据。标明哪些信息来自复现、测试、日志或报告，哪些尚未验证。

## 2. 复现和定位

优先用稳定、范围小的步骤复现。沿失败路径检查相关实现、数据状态和依赖行为，区分直接触发点与根本原因。若无法复现，记录已检查条件、现有证据和下一项最有价值的调查，不凭猜测声称定位完成。

## 3. 修复

- 修复根因，保持改动在问题边界内。
- 检查同一原因是否影响相邻路径或状态；不要借机扩大为泛化重构。
- 根据问题类型和项目约定选择回归证据。适合时补充能表达预期行为的回归检查；不为了流程形式机械增加测试。
- 若真实修复需要改变产品行为、公共接口或数据语义，回到澄清/功能/迁移路由，更新范围。

## 4. 验收

再次执行能够复现问题的场景，并按影响范围做必要的相关验证。区分“修复后未再复现”“回归验证通过”与“根因已证明解决”；只报告证据支持的结论。若验证失败，回到调查阶段，避免继续堆叠补丁。
