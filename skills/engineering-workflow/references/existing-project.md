# 存量项目

适用于已有代码、接口、数据、运行环境或用户行为需要延续的工作。它也适用于在存量仓库中新增组件：先建立宿主系统的现状、约束和集成边界，再对组件本身采用适合的建设流程。

## 调查基线

1. 查看工作区状态、相关文件和项目级约定。
2. 沿目标行为检查入口、调用链、数据结构、配置、依赖、接口和相关测试/文档。
3. 用测试、运行结果或日志等证据确认本次涉及的当前行为。
4. 识别兼容性、数据持久化、安全边界、部署和失败影响中与本次任务相关的部分。

## 定义本次变化

对比当前行为与用户要求的目标行为，明确改变范围、保留行为和验收信号。若目标与既有接口或数据约定冲突，先调查其使用方及兼容要求；重要歧义按 [clarification.md](clarification.md) 处理。

据主要变化转入 [bugfix.md](bugfix.md)、[feature.md](feature.md)、[refactor.md](refactor.md)、[migration.md](migration.md)、[performance.md](performance.md) 或 [exploration.md](exploration.md)。多个类型并存时拆解为可验证的部分，保留它们之间的依赖关系。

如果目标组件本身尚无稳定实现，完成上述宿主调查后，再按新项目的思路建立其最小骨架；这不是把整个仓库重新当作新项目。

## 修改与验证

- 尽量局部修改，遵循项目现有结构和命名，不顺手重写无关区域。
- 对可能破坏当前行为的改动，先找可用的行为保护证据；缺失时选择与风险相称的验证方式。
- 验证按用户要求与项目约定执行；说明未覆盖的部分和原因。
- 如果调查发现现状与原先假设不同，更新计划或澄清结论后再继续。
